# 父级数据成果审查

用于以后新建、需要独立审查的外层数据操作。按操作选择启用；不扫描、改写或重跑现有任务。不用于用户实验、普通聊天或自主后台任务。

## 启用

在 `work add <UTF-8 JSON文件路径>` 的请求中加入：

```json
{
  "title": "分析这一批测量并形成研究判断",
  "profile": "data-analyst",
  "actor": "codex",
  "goal": "用户要回答的问题、已有资料入口与交付目的",
  "result_review": {"reviewer": "data-reviewer", "actor": "claude"}
}
```

开关是 `result_review`，必须写 `reviewer`，指定用哪一种审查者（`prompts/profiles/` 下名字以 `-reviewer` 结尾的 profile，现有 `data-reviewer`）；不写、写 `true` 或写不存在的名字都会报错并列出可选项，操作没有类型，审查者只由这里的 `reviewer` 决定。被审查的父级可以带自己的 profile（如 `data-analyst`）；它对审查者意见的配合要求由程序随 `result_review` 放进父级的任务说明，不是单独的 profile。其余可选：`actor`（不写则与父级相同）、`model`、`effort`。每次审查都是独立的新会话。不写 `result_review` 或写 `false` 保持普通操作。审查配置不向 `parent_id` 子操作继承；子操作按研究需要自主组织，不变成固定的分析／检查双节点。

## 审查角色（profile）

分类：**profile 是“谁、审什么”，skill 是“怎么做”；每类任务一个自己的审查者 profile，不共用基底。**

| 东西 | 在哪 | 内容 | 谁能用 |
|---|---|---|---|
| 父级任务说明里的配合要求 | `prompts/fragments/task/result-review-owner.md` | 被审查者的配合：默认试审查意见里的路、把已试路线记录写进成果目录的文件（handoff 只写路径） | 启用 `result_review` 的父级自动带 |

其他种类的审查者（文献调研、实验设计等）现在没有。审查者的立场（多激进、看什么、怎样算通过）取决于那类工作你想要什么，有了要求再加 `prompts/profiles/<名字>-reviewer.md`，开关里写这个名字即可，不用改代码。


## 实际执行

1. 父级自己完成或组织子 DCG，收回证据并形成整体成果，照常提交 `work update` 的 `status:done`、`handoff`、`outputs`。
2. 程序记录本版目标、接续方向、结果说明和实际成果内容版本，在外层 DAG 创建独立审查操作。审查与父级并列，实际前置指向父级；不占用父级内部的子 DCG。与此同时，用现有 `work run / after` 机制登记回到原父级会话。
3. 审查者扮演激进的功利主义 PI：一切为了把用户要的量从现有数据里处理出来。把目的拆成要交的每个量，逐项看有没有处理出来；没有的，读成果里最后一步的处理后数据（逐点表、画图所用的表、导出文件，必要时自己画图），找到卡点，再提出能绕过去的路，可以很激进，只要现有数据能做、假设写明。每个量要么处理出来（带明说假设的暂定值也算），要么最后一步的数据证明现有数据取不到且可行路线已试过，才通过。不读取仪器原始文件，不接手逐点复算；返工时给父级具体问题、卡点、建议路线和预期得到的量，执行路线由父级组织。可以连续退回，每轮对照用户目的重新逐项判断，不增派用户实验。审查证据写自己的运行目录，不改被审查成果。
4. 审查者一次提交自己的结果：

```json
{
  "id": "审查操作ID",
  "status": "done",
  "review_verdict": "pass",
  "handoff": "具体判断及证据入口；需要返工时写具体缺口",
  "outputs": ["本次审查证据文件"]
}
```

`review_verdict` 为 `pass` 或 `revise`。完成执行、提交审查结果、通过审查是不同事实；缺少明确判定不放行。审查时核对实际成果仍是本版，旧版结论不能提交给新版。
通过表示本轮成果的研究推进程度达到交付要求，不表示审查者做过原始数据核验或数值复算。

5. 审查本次执行结束后，成功、失败、取消或未提交都会返回原父级。通过后由父级核对整合，沿用本版原 `handoff`、`outputs` 再提交 `status:done`，才释放后继。返工意见交父级负责人，由对方组织修订；新版本提交后安排新一轮审查，不重做未受影响的子成果。

每一轮审查都是新开的独立对话：新版本提交生成新的审查操作，不接续上一轮的会话；对同一审查操作再 `work run`（例如执行失败后重试）也新开对话，不带上次的会话历史，并撤下该审查的旧判定。父级对审查意见有异议时，把具体证据写进 handoff 重新提交，由程序新开一轮审查。执行失败不会自动重试，没有轮数到了自动通过的逻辑。

## 少重复搬运，保留独立判断

父级在首批研究证据返回时就检验关键解释与分支连接，先用实际图数和简洁整体稿暴露路线问题，再投入精装交付；不新增固定内部检查层或例行模型调用。数据浏览照常推进，正式成果仍由原外层审查判断。

首次审查看整体；后续新版本的审查输入只给出本版与上一次送审版本的路径/哈希和登记文字变化，不含上一轮审查的 ID、判定和证据入口，避免成为新审查的锚点。它只负责导航，不判断科学影响或继承旧版通过。换目录表现为新增/未再列入；未列入 outputs 的依赖变化不在文件比较中。

复审先独立检查上轮问题对应的新证据，沿共享前提和结论的实际影响范围扩读；保留未受影响且仍成立的依据，不例行重读全部历史，也不把上轮意见当作可发现问题的上限。大表先程序筛选再读。报告、图和浏览器复用同一份结果，补分析只更新受影响部分，并在最终交付核对整体一致。版本冻结、明确判定和父级最终整合机制不变。

## 状态与范围

`work handoff` 保留审查对象、版本、判定和执行历史；`work list review` 可查看尚待审查或父级处理的成果。项目 DAG 在父级旁显示独立审查，父级内部仍显示自己的动态子操作。

父级初次提交后的 `done` 表示分析成果已提交；`result_review` 的 `pending / pass / revise` 分别显示待独立审查、待父级整合、待父级返工。最终整合为 `accepted` 后，依赖父级成果的后继才可执行。这不替代用户审批或已有验收卡。

成果文件或目录按实际内容标识版本；审查证据放在其外，避免改动被审查版本。更换研究问题、接续方向、结果说明或成果内容后，需要对应的新审查。程序不决定科学结论、不替审查者增加研究目标，也不直接指挥父级子操作。

代码发布随后台下一次安全重载生效；不在正在运行的任务中重启后台。

开发验证入口：`node scripts/run-tests.mjs --result-review`，使用虚构数据和假模型返回，在脱敏副本验证父级、动态子 DCG、独立审查、返工、版本和回原会话的实际调度路径，不调用真实模型。
